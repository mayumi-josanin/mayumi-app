**まだ決めていない項目は最後の「決めていただきたいこと」にまとめてある。**

- 前提: PostgreSQL（KEM_DDENKI と同じ構成を借りる）
- 方針: **お客様の入り直しをゼロにする**（[README](../README.md) の「ログインの仕組み」を保つ）

## 移行で直す3つのこと

### ① パスコードが平文で保存されている

いまの `パスコード` 列は **数字がそのまま入っている**（137名分）。スプレッドシートを開ける人は全員の暗証番号を読める状態。

移行時に**塩＋ハッシュに変換**する。移行スクリプトが平文を読める最後の機会なので、ここでやるのが一番きれい。

**お客様への影響はゼロ。**いまのパスコードがそのまま使え、入り直しも不要。

### ② ビジリスと会員が「お名前の文字列」で紐づいている

測定履歴の `会員番号` は 43行中 **1行しか埋まっていない**。実際の紐づけはお名前の一致頼み。
「山谷 → 山谷未央」の改名で専用スクリプトが必要になったのはこのため。

移行時に **member_id で紐づけ直す**。改名しても記録が切れなくなる。

> 移行手順: お名前で突き合わせ → 一致しないものを一覧で出す → 目で確認して割り当て。
> 42件しかないので確認は現実的。

### ③ 同じ意味の列が2つある

`最終スタンプ取得日`(126) と `最終スタンプ取得日時`(122)、`引き継ぎコード発行日時` など、
シートを継ぎ足してきた結果の重複。移行時に1本化する。

## 入り直しをゼロにするための約束

移行後も**この3つを必ず保つ**。

| | 保つもの |
|---|---|
| 1 | `ADMIN_TOKEN_SECRET` と札の形式（`base64url({t,u,exp,sig})` / HMAC-SHA256）→ 発行済みの札が通る |
| 2 | 会員ID → スタンプ・回数券・測定履歴が続く |
| 3 | 画面のURL（GitHub Pages のまま）→ ホーム画面のアイコンが生きる |

切替前に**「GASが作った札を新しい側が同じと判定するか」を実データで突き合わせる試験**を通す。
これが合わない限り切り替えない。

## 写真をどうするか

いま写真は Google ドライブにあり、シートには URL が入っている（計測写真・ビフォー/アフター）。

**当面はドライブのままにする。**DBには URL と ファイルID だけを持つ。

- 移行対象が減り、切替の risk が小さい
- 院長がドライブから直接見られる運用が変わらない
- 将来まとめて移したくなったら、URL列を差し替えるだけで済む

## 決まったこと（2026-08-14）

### A. 使っていない3機能 → **作らない**

注文管理・サポートチャット・お知らせテンプレートは、いずれも一度も使われていない（0件）。
新しい方には作らない。必要になったらそのとき足す。

→ **3テーブル・61列ぶんの設計と画面が不要になる。**

### B. 操作履歴 → **人の操作ぶん（約760行）だけ移す**

中身を数えた結果、**9,562行のうち92%が自動処理の記録**だった。

| 種別 | 件数 | 内容 |
|------|------|------|
| **syncUserDeviceSession** | **7,993** | 端末の記録合わせ。アプリが勝手に行う |
| **syncUserRewardStatus** | **807** | 特典状態の同期。同上 |
| recoverAccount | 140 | パスコード復旧 |
| updateUser | 137 | 会員情報の編集 |
| addBlog | 69 | お知らせ追加 |
| saveMenuRevenueRecord | 60 | 売上記録 |
| updateAdminRewardStatus | 59 | 特典の手動変更 |
| deleteUser | 42 | 会員削除 |
| resetForgottenPasscode | 39 | パスコード再設定 |
| addCalendar / updateBlog / deleteOrders | 38 / 30 / 30 | |

- 期間: 2026-05-14 〜 2026-08-14（93日）
- 結果: 成功 9,286 / 失敗 276
- 操作者: 全件「管理者」（誰がやったかは記録されていない）

**上の2種を除いた約760行だけを移す。**93日ぶん全部でもこの量。

> **ついでに直したいこと**: この2種は今後も記録しない方がよい。
> 93日で8,800回の書き込みは、シートを太らせるだけで誰も見ない。
> 「操作者」が常に「管理者」なので、監査の役にも立っていない。

### C. アンケートの設問 → **JSONB のまま持つ**

いまの作りに近く、設問を変えてもテーブル変更が要らない。

### D. 最初に移すのは → **管理側だけ**

お客様側は当面いまのまま。管理側が安定してから判断する。

## 次にやること

上のA〜Dが決まったら、**移行スクリプトの下書き**（読み取り専用の突き合わせ）から始める。
実データを1件も変えずに「何件移せて、何件が突き合わない」だけを出せるので、
移行しない判断をしても無駄にならない。
