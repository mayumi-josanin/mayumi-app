# 管理画面（Django 版）

GitHub Pages の管理アプリ（`admin/index.html`）を、サーバー上の Django へ
1画面ずつ移している。**GAS を通らない。**この Django が直接データベースを読み書きする。

## 開き方

Tailscale の中からだけ。院の端末は Tailscale が ON になっていること。

    https://desktop-rmsk0vg.tail8efe0d.ts.net:10002/manage/

役割（まゆみ／スタッフ）を選んでパスコードで入る。予約システムの管理画面と同じ。

**Funnel（mayumi-api.tail8efe0d.ts.net）には出ていない。**`/manage/` は
`MANAGE_ENABLED` を立てた `manage` の箱だけが持ち、その箱を
`tailscale serve --https=10002` で Tailscale の中にだけ出している。

## パスコードを決める・変える

サーバーPCで（Git Bash でも PowerShell でも）:

    cd projects/mayumi-app/server
    docker compose exec -T -e MANAGE_PASSCODE=（4桁以上） manage python manage.py manage_passcode owner
    docker compose exec -T -e MANAGE_PASSCODE=（4桁以上） manage python manage.py manage_passcode staff

`owner` がまゆみ、`staff` がスタッフ。アカウント名は役割名そのもの。
パスコードは引数に書かない（履歴に残る）。環境変数で渡す。

5回続けて間違えると15分待たされる（`apps/manage/middleware.py`）。

## 通知（OneSignal）

サーバーPCの `server/.env` に、GAS のスクリプトプロパティと同じ2つを入れる:

    ONESIGNAL_APP_ID=...
    ONESIGNAL_REST_API_KEY=...

入れたら `docker compose up -d manage` で読み直す。無ければ送らず、画面にその旨が出る。
送った記録はサーバーの通知の表（PushNotice）に「自動送信済み」で残る。
SERVER_TABLES に `push` を入れると、GAS の broadcastPush / sendAutoPush / 5分ごとの予約送信 /
通知履歴の削除がサーバーへ転送され、旧管理アプリ・お客様アプリの通知一覧もサーバーの表を見る。
入れる前に `掲載物を書き出す()` → `掲載物を取り込む <json> --only push_notices` でシートの残りを取り込む
（`--only` を付けないとお知らせ等の新しい行が古いシートの値で上書きされる）。

### 予約したお知らせは、サーバーが1分おきに見て送る

**GAS の自動実行には頼らない。**`cron` の箱（`docker-compose.yml`）が1分おきに

    python manage.py 予約した通知を送る

を呼び、予約日時が過ぎていてまだ送っていないものを古い順に送る（`--下見` を付けると
送らずに件数と中身だけ出る）。**送る前に「送った」印を立ててから送る**ので、
GAS の自動実行（状態が「予約済み」の行だけを拾う）と重なっても二度は届かない。

2026-09-20 まで、時間が来たときに送る役目は GAS の自動実行だけが担っていた。
その GAS が 9/18〜20 の2日間で6回、名前引き（DNS）の失敗で落ちている。
予約が1件も無かったので実害は出ていないが、次の予約は時間どおりに届かない恐れがあった。

送れなかったものは「送信失敗」と理由を履歴に残し、**やり直さない**
（届かないまま毎分試し続けないため）。同じ内容で送り直すのは画面から。
通知の鍵（ONESIGNAL_*）は `cron` の箱にも要る。無ければ送らずに理由を記録して終わる。

## 予約管理（mayumi-reserve）との行き来

左メニューの「予約」（予定表・予約の管理・お客様）は、予約システムの管理画面（:10001）へ
**ログインし直さずに**移る（`apps/manage/sso.py`）。予約管理側の「アプリ管理へ」も同じ。
両方の `.env` に同じ `MANAGE_SSO_SECRET`（長い適当な文字列）を入れる:

    setkey.ps1 MANAGE_SSO_SECRET <文字列>           （mayumi-app/server/.env）
    setkey_reserve.ps1 MANAGE_SSO_SECRET <文字列>   （mayumi-reserve/.env）

空なら受け渡しは動かず、相手のログイン画面に着く（メニュー自体は出る）。
札は60秒で切れ、一度使ったものは受け付けない。役割（まゆみ／スタッフ）は相手側の同じ役割の人として入る。

## 画像

`media/news/`・`media/menus/`・`media/products/`・`media/calendar/` に置き、Funnel 側の `/media/<置き場>/<名前>` で配る（`apps/gasapi/media.py`）。
`manage` と `web` は同じ volume（`mayumi_media`）を見ている。
大きな写真は 1600px に縮めて JPEG にする（`apps/manage/images.py`）。

    cd server

`config/settings_test.py` が SQLite・`MANAGE_ENABLED` で立てる。

## サーバーへ反映する手順

**1行で済む。**

    bash ~/projects/mayumi-app/server/scripts/deploy.sh

中で、下の手順をこの順に流している。最後に「配られる中身が、いまのコードと同じか」を
確かめて知らせる。依存（Pillow など）が変わっていなければ、箱の作り直しは飛ばす。

コードを置き場ごと箱に載せている（`.:/app`）ので、**ビルド時に集めた CSS は隠れる。**
箱の中で集め直してから再起動する（予約システムの deploy.sh と同じ順）。

    cd projects/mayumi-app && git pull --ff-only origin develop
    cd server
    docker compose build web manage          # 依存（Pillow など）が変わったときだけ
    docker compose up -d manage
    docker compose exec -T manage python manage.py migrate --noinput
    docker compose exec -T manage python manage.py collectstatic --noinput
    docker compose restart manage web

**集め直す → 起動し直す、の順は変えないこと。**逆にすると、箱は古い一覧を覚えたまま
動き続ける（WhiteNoise は起動のときに数える）。2026-09-22、摘要の直しが
`collectstatic` 抜けで届かず、iPhone に古い画面が出ていた。手順を覚えていなくても
済むように、上のスクリプトにまとめた。

Tailscale への公開は一度だけ（再起動後も残る）:

    tailscale serve --bg --https=10002 http://127.0.0.1:8005

## スタッフのログイン（2026-09-16）

スタッフは管理画面（:10002）でログインできるが、**見えるのは予約管理だけ**。ログインするとそのまま予約システムへ
受け渡され（go_reserve）、予約システムの左メニューは「予約」のまとまりだけになる。アプリ管理・公式サイト・開発の画面は
すべて `owner_required` で 403。左メニューの出し分けは `apps/manage/navigation.py`（まゆみ以外には予約管理の段だけ）。
