## 3段階に分ける

**一度に全部は移さない。**危険度が違いすぎる。

### 第1段（読むだけ・危険が小さい）

```
getAdminUsers   getPushUsers   checkMemberToken
```

読むだけなので、間違えても表示が変わるだけ。**まずここで仕組みを確かめる。**
`getPushUsers` は通知の配信に使われるので、**空を返さないこと**を必ず確認する。

> 8列目は「オン/オフ」ではなく**届け先そのもの**。真偽値にすると通知が届かない。
> 2026-08-23 に取り込みの取りこぼしとして見つかっている。

### 第2段（管理側の書き込み）

```
handleUpdateAdminUser   handleUpdateAdminRewardStatus
handleDeleteUser        handleGrantSurveyStamp
handleIssueTransferCode handleMergeUsers
```

受付が使う。**間違えても、その場で気づける。**`handleMergeUsers` は
他の表も触るので最後に回す。

### 第3段（お客様の入口）— **いちばん危ない**

```
loginAccount   registerAccount   registerBijirisUse
```

**ここが止まると、お客様がアプリに入れなくなる。**

- 会員IDの採番を間違えると、**別の方の記録に上書きする**
- パスコードの照合を間違えると、**全員が入れなくなる**
- 札の作り方を変えると、**発行済みの札が全部無効になる**（`ADMIN_TOKEN_SECRET` を変えないこと）

**第1段・第2段が数日おかしくないことを見てから**着手する。

## 9/19〜23 の割り当て

```
9/19(土)  会員データを書き出す → 取り込む → **本番と全項目を突き合わせる**
          第1段（読むだけ3つ）を作って切り替える
9/20(日)  第1段を見守る。第2段を作る
9/21(月)  第2段を切り替える。**戻す判断の期限は月曜の夜**
9/22(火)  第3段を作る（入口）
9/23(水)  第3段を切り替える。**翌日から通常診療なので、ここが最後の砦**
```

**第3段が間に合わなければ、そこだけ次の休みに回す。**
会員の表は「読みはサーバー、入口はシート」でも一日は保つ。
（読みが古くなるだけで、入れなくなるよりはるかにましだから）

## 当日に必ずやること

1. **パスコードの下見。**「短くなっている」が0名であること
   - GAS は照合時に0を補うが、**サーバーはハッシュなので補えない**
   - 壊れたまま切り替えると、その方は入れなくなる
2. **会員データを書き出す → 取り込む**（直前に。日々増えている）
3. **会員ごとの印を書き出す → 取り込む**（移し忘れるとお礼スタンプが二重に付く）
4. **控えを取る**（データベースのダンプ ＋ スプレッドシートの複製）
5. **突き合わせ。**件数だけでなく**全項目**を見る
   - お知らせでは、件数が合ったあとに画像・ボタン・時刻の3つが違っていた
   - カレンダーでは**カテゴリ70件**がまるごと落ちていた

## 戻し方

`SERVER_TABLES` から `member` を消すだけ。**デプロイは要らない。**

戻したあと、切り替えていた間にサーバーへ書かれたぶんはシートに無い。

```
端末の記録合わせ            消えてよい（次に開けば書き直される）
スタンプの同期              消えてよい（端末側にも残っている）
**新規登録**                **消えてはいけない**
**復元・パスコード再設定**   **消えてはいけない**
```

サーバーの `操作履歴` と `会員` の**行番号が空の行**を見て、手でシートへ写す。
（行番号が空 ＝ サーバーが自分で作った記録）
