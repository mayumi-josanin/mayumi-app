# 1つにまとめる（リポジトリ・公開先・データベース）

**2026-09-17。院長と決めたこと。** 着手は **9/19 の会員移行のあと、1週間ほど様子を見てから。**

いまは作る場所が4つに分かれている。管理画面と予約システムのように、
片方を直すと必ずもう片方も直すものが別の場所にあり、出すのも2回に分かれる。
その間だけ食い違う時間ができる。

---

## 決めたこと（3つ）

### ① 作る場所は1つ、公開先は今のまま

```
mayumi（作る場所。develop と main の2本だけ）
  apps/customer   お客様アプリ    ──→ mayumi-app（公開用）    GitHub Pages
  apps/site       公式サイト      ──→ mayumi-site（公開用）    GitHub Pages
  apps/bijiris    ビジリス        ──→ ビジリスの公開用         GitHub Pages
  services/manage  管理画面       ──→ 自宅サーバー
  services/reserve 予約システム   ──→ 自宅サーバー
  gas/            スプレッドシートの仕掛け ──→ Google
  docs/
```

**1つのリポジトリが持てる公開サイトは1つだけ。** 公開するものは3つあるので、
`main` に入ったら、出来上がったファイルだけを公開用のリポジトリへ送り出す
（GitHub Actions）。送り先は**いまのリポジトリをそのまま使う**ので、
**お客様から見える住所は1文字も変わらない**。
ポスターのQRも、ホーム画面に追加した方のアプリも、そのまま届く。

住所を変えない理由: QRは刷って配ってあり、ホーム画面に入れた方の入れ直しは頼めない。

### ② 行けるところは全部 GitHub Pages へ

| もの | 動く場所 | データ |
|---|---|---|
| お客様アプリ | GitHub Pages | 自宅サーバーに聞きに行く |
| 公式サイト | GitHub Pages | 持たない |
| ビジリス | GitHub Pages | 自宅サーバーに聞きに行く |
| 管理画面 | 自宅サーバー（院内だけ） | 自宅サーバー |
| 予約システム | 自宅サーバー（予約画面だけ外へ） | 自宅サーバー |

Pages に置けるのは**見た目だけ**のもの。データベースを持つ2つは置けない。
公式サイトはまだ FTP（ヘリオス）なので、ここで Pages へ移す。
ヘリオスは 2027年5月末で満了、申し込みの期限は 2027年3月末（[[mayumi-hp-helios-cancellation]]）。

### ③ お客様の情報は1つのデータベースへ

お客様アプリ・ビジリス・管理画面は**すでに同じデータベース**を見ている。
予約システムだけが別を持ち、窓口越しに台帳へ1行送っている。
これをやめ、**予約システムも同じデータベースを見る**。

> **9/08 の決めごとを、院長の判断で変えた。**
> [お客様台帳を1つにする](お客様台帳を1つにする.md) では「1つの表にはまとめない」と決めていた。
> 理由は予約システムを他院に売る前提だったから。
> 2026-09-17、院長が「**外販はもうしない。まゆみ専用にする**」と決めた。
> よって同じデータベースに寄せる。
> サロン向けの版（`sonomako2026/salon-reserve`）はすでに別のリポジトリなので、
> そのまま動き続ける。**ただし、これ以降こちらの直しは自動では届かない。**

**外に出ている箱の守り。** 予約システムは、お客様の予約画面をインターネットに出している。
いまはデータベースが分かれているので、万一その入口を破られても台帳までは届かない。
1つにするとその壁が無くなるので、**外向けの箱（gate）には、予約の表だけを読み書きできる口を渡す**。
台帳の表には手が届かないようにする（PostgreSQL の権限で決める）。壁は作り直せる。

**値打ち。** いまは名前と電話で突き合わせて同じ方かどうかを判断しており、
ここが一番ほころびやすい。1つにすれば二重登録の悩みが根本から消える。

### やらないこと

- **母乳相談カルテ**（`josanin-karte`）は使わなくなったので、まとめる対象から外す。
