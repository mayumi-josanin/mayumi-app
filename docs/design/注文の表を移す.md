# 注文の表を移す

**2026-09-05 の下調べ。**院長から「アプリからの商品注文を使う予定がある」と伺った。

段取りは [表を移す手順](表を移す手順.md)。

---

## いまの状態

```
注文の記録   **0件**（一度も使われていない）
```

[移行設計] は「注文の表は作らない」と判断していた（判断A）。
使う予定があるなら**作る。**ただし**急がない。**0件なので、
移すべきデータが無い。**会員の表を先に片付けてからでよい。**

## いちばん厄介なところ

`handleOrder` は、注文を書くときに**スプレッドシートの数式**を入れている。

```js
`=IFERROR(VLOOKUP(D${r}, '${SHEETS.MASTER}'!A:B, 2, FALSE), 0)`   // 仕入値
sheet.getRange(r, 13).insertCheckboxes();                          // 受取確認
```

**データベースに数式は無い。**仕入値は書き込むときに計算して入れる
（`_原価の表()` が既にある。商品名で引く形も同じ）。
チェックボックスは真偽値の列にする。

**「シートだからできていたこと」を、書き込み時の計算に置き換える。**
この置き換えを間違えると、**粗利の数字が静かにずれる。**

## `getAnalyticsData` が道連れになる

292行あり、注文・売上・仕入・メニュー収益をまとめて読んでいる。
注文だけを移すと、**分析画面が注文を0件として計算する。**

いまは注文が0件なので害が無い。**注文を使い始める前に、ここも一緒に移す。**
「1つ移すと、その応答に相乗りしている表も道連れになる」の典型
（お知らせを移してカテゴリが食い違ったのと同じ形）。

## 進め方の案

```
第1段  Order の表を作る（15列）＋ 読む窓口3つ
       getCustomerOrders / getAdminOrders / getAdminUserOrders
       **0件なので、間違えても何も起きない**

第2段  書く窓口4つ
       handleOrder / handleCancel / handleConfirmReceipt / handleUpdateOrder
       **仕入値の計算をここで置き換える**

第3段  管理と分析
       updateAdminOrder / handleDeleteOrders / buildOrderStatsByMemberId_
       **getAnalyticsData**（いちばん大きい）
```

## いつやるか

**会員の表（9/19〜23）のあと。**理由は3つ。

1. **注文は0件。**移すべきデータが無く、急ぐ理由がない
2. 会員は 9/19 の休みでないと動かせない。注文はいつでもできる
3. `handleMergeUsers` が注文にも触るので、**会員を移すときに
   注文の形が決まっている必要はない**（統合は会員側の処理）

**注文を使い始める前に終わらせる。**使い始めてから移すと、
移行中の注文をどちらに書くかで悩むことになる。
