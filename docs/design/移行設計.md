## 移行で直す3つのこと

### ① パスコードが平文で保存されている

いまの `パスコード` 列は **数字がそのまま入っている**（137名分）。スプレッドシートを開ける人は全員の暗証番号を読める状態。

移行時に**塩＋ハッシュに変換**する。移行スクリプトが平文を読める最後の機会なので、ここでやるのが一番きれい。

**お客様への影響はゼロ。**いまのパスコードがそのまま使え、入り直しも不要。

### ② ビジリスと会員が「お名前の文字列」で紐づいている

測定履歴の `会員番号` は 43行中 **1行しか埋まっていない**。実際の紐づけはお名前の一致頼み。
「山谷 → 山谷未央」の改名で専用スクリプトが必要になったのはこのため。

移行時に **member_id で紐づけ直す**。改名しても記録が切れなくなる。

> 移行手順: お名前で突き合わせ → 一致しないものを一覧で出す → 目で確認して割り当て。
> 42件しかないので確認は現実的。

### ③ 同じ意味の列が2つある

`最終スタンプ取得日`(126) と `最終スタンプ取得日時`(122)、`引き継ぎコード発行日時` など、
シートを継ぎ足してきた結果の重複。移行時に1本化する。

## 入り直しをゼロにするための約束

移行後も**この3つを必ず保つ**。

| | 保つもの |
|---|---|
| 1 | `ADMIN_TOKEN_SECRET` と札の形式（`base64url({t,u,exp,sig})` / HMAC-SHA256）→ 発行済みの札が通る |
| 2 | 会員ID → スタンプ・回数券・測定履歴が続く |
| 3 | 画面のURL（GitHub Pages のまま）→ ホーム画面のアイコンが生きる |

切替前に**「GASが作った札を新しい側が同じと判定するか」を実データで突き合わせる試験**を通す。
これが合わない限り切り替えない。

## 進め方（表を1つずつ引っ越す）

### 置き場所

**KEM_DDENKI のPC（`desktop-rmsk0vg`）に Django + PostgreSQL を置き、Tailscale Funnel で公開する。**

Funnel は公開のHTTPSなので、**Googleのサーバー（GAS）からも届く**。
以前「VPSが必要」と書いたが、それは誤り。

> **前提条件（移行前に必ず済ませる）**
> このPCは Docker Desktop が「サインイン時に自動起動」の設定になっており、
> 再起動後に誰かがWindowsにサインインするまで PostgreSQL が上がらない。
> 停電から復電しても、翌朝まで止まったままになりうる。
>
> 1. BIOS/UEFI で「電源復帰時に自動起動」（`Restore on AC Power Loss` → Power On）
> 2. Windows の自動サインイン（`netplwiz`）
> 3. スリープしない設定
> 4. 併せて BitLocker か画面ロックで、目の前の人には鍵をかける
>
> **3つ揃わないと意味がない。**①が無ければ②③は動かない。

### GAS は窓口として残す

```
お客様のアプリ ─┐
                ├→ GAS ─┬→ Funnel → PostgreSQL（引っ越し済みの表）
管理アプリ ─────┘        └→ スプレッドシート（まだの表）
```

| 役割 | |
|------|---|
| GAS | **窓口。**アプリから見た話し相手は最後まで変わらない |
| PostgreSQL | 引っ越した表の**唯一の正** |
| スプレッドシート | まだの表の**唯一の正**。引っ越した表は書き出し用の控えに変わる |

**どの表も、住んでいる場所は常に1つだけ。**だからズレようがない。

これにより、
- お客様の**入り直しはゼロ**（札もURLも触らない）
- 1回の切り替えは**表1つ分**。おかしければその表だけ戻す
- 約160の窓口を一度に書き直さなくてよい

### 表の分け方の原則

**「1人に1つ」か「1人に何個も」か**で決める。

| | 例 | 置き場所 |
|---|---|---|
| 1人に1つ | 氏名・電話・住所・パスコード・スタンプ数 | **会員台帳（members）** |
| 1人に何個も | 計測・アンケート回答・回数券分析 | **別々の表** |

計測履歴を会員台帳に入れられないのは、1人が何回も測るため。

> **会員登録情報は、必ず1か所だけに置く。**
> ビジリス側にも氏名を持つと、まゆみ側と表記がズレて別人になる。
> 「小瀬村真理子 / コセムラマリコ」がまさにこれだった。
>
> **スタンプは2種類ある。**まゆみのスタンプカード（会員台帳）と、
> ビジリスの回数券（ビジリス側）は別物。混ぜない。

### 引っ越す順番

**止まっても困らない表から。**会員データは最後。

| # | 表 | 件数 | 止まったときの影響 |
|---|----|------|------------------|
| 1 | **測定履歴** | 42 | ビジリス管理で見られないだけ。**お客様に影響なし** |
| 2 | 回数券分析結果 | 15 | 同上 |
| 3 | アンケート回答 | 0〜 | 送信できない |
| 4 | お知らせ・カレンダー・商品 | 200超 | 表示できない |
| 5 | 売上・仕入 | 197 | 院内のみ |
| 6 | **会員データ** | 158 | **誰もログインできない** |

①を移したあと **2〜4週間動かし、実際に何時間止まったかを測ってから**、
会員データを移すか判断する。止まる頻度が高ければ VPS（月500〜1,000円）へ切り替える。
Django ごと引っ越すだけなので、あとからでも難しくない。

### 表1つの引っ越し手順（毎回これを繰り返す）

1. Django にその表のモデルを作る
2. **読み取りだけ**のAPIを立て、GASから読めることを確かめる
3. スプレッドシートから中身を写す（件数を突き合わせる）
4. GASの**読み取り**をAPIに切り替える。書き込みはまだシート
5. 1週間ようすを見る
6. GASの**書き込み**もAPIに切り替える
7. シート側は「夜間に書き出す控え」に変える（手で書いても反映されない旨を明記）

**問題が出たら、その表だけ手順4の前に戻す。**他の表には影響しない。
