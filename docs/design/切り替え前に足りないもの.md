## 塞ぐ順番

### 1. `uploadImage` — **必ず要る**

11名が写真を使っている。休みのあいだに誰かが変えようとして失敗する。

**受け皿がまだ無い。**サーバーには `MEDIA_ROOT` も `MEDIA_URL` も、
画像を残す入れ物（docker の volume）も設定されていない。次が要る。

```
① settings に MEDIA_ROOT / MEDIA_URL
② docker-compose に volume（作り直しても消えないように）
③ /media/ を配る経路（Django は本番で自動では配らない）
④ writes.py に uploadImage
```

**GAS はリンクを知れば誰でも見られるURLを返している**（Drive の共有リンク）。
サーバーでは推測できないファイル名にする。閲覧の制限は別の話として後で行う。

### 2. `unsubscribePush` — 要る

届け先を持つ方は0名だが、**通知を切れないのは困る。**
「切りたい」に応えられないのは、機能の欠落ではなく信頼の問題。

### 3. `order` / `cancel` / `confirmReceipt` — 判断が要る

**注文は0件。一度も使われていない。**[移行設計] でも「注文の表は作らない」と
判断済みで、読み取り窓口 `getCustomerOrders` は常に空を返している。

選べる道は2つ。

| | やり方 | 結果 |
|---|---|---|
| A | 3つとも作る | 注文機能が使えるようになる。作りは大きい |
| B | アプリから注文の画面を消す | 使っていない機能が消える。作りは小さい |

**院長に伺う。**使う予定が無いなら B が正しい。
「いつか使うかもしれない」なら、切り替えとは別に A を進める。

## この調べ方は、切り替えのたびに繰り返す

**窓口の数が合っていても、名前が合っているとは限らない。**
今回も、公開してよい一覧（`公開アクション`）には5つとも載っていたのに、
**実装（`書けること`）には無かった。**一覧に載っているだけでは動かない。
