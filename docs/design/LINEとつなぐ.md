# LINEとつなぐ

**2026-09-08 の下調べ。**院長から
「お客様アプリにログインした方で、LINEIDが登録されていない人に
友だち登録のご案内を出せないか。そうすればLINEIDを取得できる」と伺った。

**着手は 9/19 のあと**（院長のご判断）。会員の表がサーバーへ移ってから作る。
いま作ると保存先がスプレッドシートなので、9/19 に作り直しになる。

---

## いちばん大事なこと

**「友だち追加してください」の案内だけでは、LINEIDは取れない。**

友だちになると、LINEから当院へ webhook が届く。
中身は「`U1fd6…` が友だちになった」だけで、**それが誰かは書いていない。**

これはポチコで当たった壁とまったく同じ（[ポチコの顧客を結ぶ] 参照）。

```
友だち          484名   IDは分かる。誰かは分からない
ポチコで予約     261名
  表示名で一意   180名
    本名も取れる 131名   ← 突き合わせられたのはここだけ
  友だちにいない  75名   ← 手が届かない
```

案内を出して友だちが増えても、**「増えたIDが誰か」を当てる作業がまた発生する。**
表示名で当てるのは同姓同名と同じ危険を持つ（CLAUDE.md「お名前でお客様の記録を探す」）。

## だから「LINEでログイン」にする

アプリには**すでに会員としてログインしている。**
そこで LINE ログインを1回挟めば、**どの会員のIDかが確実に決まる。**推測が要らない。

```
① アプリにログイン           今のまま（会員IDとパスコード）
② LINEIDが空なら案内を出す    まだ友だちでない方にだけ出せる
③ 「LINEとつなぐ」を押す      LINEの確認画面。友だち追加のチェック付き
④ 戻ってきたら確かめて保存     サーバーがLINEへ問い合わせ、34列目へ
```

**③で友だち追加も同時に済む。**院長のお考えのご案内は、この中に含まれる。
LIFF の「友だち追加オプション」を on にすると、確認画面に友だち追加が並ぶ。
`liff.getFriendship()` で友だちかどうかを読めるので、**出す相手を絞れる。**

## 集まる道は3つある

**IDは1か所からは集まらない。**お客様の行動が3通りあるため。

```
① アプリを開く方        アプリで案内 → LINEでログイン
② 予約される方          予約システムがLINE経由なので、**予約した時点で取れる**
③ どちらもしない方      集まらない。受付でお声がけするか、諦める
```

**②がいちばん確実で、こちらから何もお願いしなくてよい。**
ポチコの置き換えが済めば、予約された方のIDは自動的にたまる。
①は、予約しない方（お知らせだけ見ている方）に効く。

## アプリの流れ

```
1. お客様がアプリにログインする            今のまま（会員IDとパスコード）
2. LINEIDが空なら、ホームの上に帯を出す
     「LINEとつなぐと、ご予約のときにお名前や電話の入力が要らなくなります」
     [LINEでつなぐ]  [あとで]

   **「LINEに届きます」と書かない。**2026-09-08 に
   「こちらからLINEで通知を送るのはやめる」と決めた（下記）。
   届かないものを書くと、つないだ方が待ってしまう。
3. 押すと LINE の確認画面へ
     すでに友だち  → 「許可する」だけ
     まだ友だち    → 「まゆみ助産院を友だち追加」にチェックが入った状態
4. アプリに戻る → **サーバーがLINEへ問い合わせて本物か確かめる** → 台帳へ保存
5. 帯が消える。設定に「LINEとつながっています」と出る
```

決めごと:

- **ログインに被せない。**帯で出す。押さなくても使える
- **「あとで」を押したら、しばらく出さない。**しつこくしない
- **お願いではなく、良くなることを書く。**「LINEIDを教えてください」ではなく
  「ご予約のときの入力が要らなくなります」
- **予約の画面でも出す。**動機がいちばん高いのはそこ

## 院長にしていただくこと（1回だけ）

LINE Developers コンソールで **LIFF を1つ足す。**
**公式アカウントと同じプロバイダーの、LINEログインのチャネル**に足すこと。
別のプロバイダーに作ると、同じ方でもIDが別物になって結べない。

```
エンドポイントURL   https://mayumi-josanin.github.io/mayumi-app/
サイズ             Full
scope              profile, openid
友だち追加オプション  On (Aggressive)   ← これで確認画面に友だち追加が並ぶ
```

できた **LIFF ID** を教えていただければ、あとはこちらで作る。
予約システムのLIFFとは**別に作る**（エンドポイントのURLが違うため）。

## こちらからLINEで通知は送らない（2026-09-08 決定）

**LINEIDを集めるのは「知らせるため」ではなく「お客様を見分けるため」。**
ここを取り違えると、文言も設計もずれる。

LINE の push は通数を使う（無料枠は月200通）。予約は直近12か月で
**平均202件/月・最大254件/月**あり、確定通知だけで枠を超える。
院長のご判断で、**こちらから送るのはやめる。**

代わりに、お客様が**見に行く**形にする。どれも0円で、すでに出来ている。

```
予約した直後   完了画面（そのまま見ている）
              「Googleカレンダーに追加」「そのほかのカレンダーに追加」
いつでも       公式LINEのリッチメニュー →  https://liff.line.me/<LIFF ID>/mine/
              **生のURLを入れない。**LINEを通らないとどなたか分からず、
              予約が1件も出ない
```

**例外が1つだけある。院の都合でキャンセル・変更したときは送る。**
お客様は知らないまま来院されてしまう。リッチメニューは見に行かないと
気づけない。件数は月に数件なので、無料枠に収まる。

## 揃っているもの・足りないもの

```
○ LINEログインのチャネル      mayumi-reserve で動いている
○ 公式アカウントと同じ提供元   2026-09-05 に確認済み
                             （違う提供元だと、同じ人でもIDが別物になる）
○ 会員シートの34列目          USER_COL.LINE_USER_ID
○ サーバーの保存先            Member.line_user_id（重複を弾く作り入り）
○ 本物か確かめる処理          mayumi-reserve の apps/booking/line.py

× LIFFの登録                  アプリのURLを登録する。**院長の作業**
× 確かめる窓口                サーバーに1つ足す
× 画面                        ご案内と、つなぐボタン
```

## 気をつけること

**① アプリが送ってきたIDを信じない。**
必ずサーバーからLINEへ問い合わせて確かめる。信じる作りにすると、
**誰でも他人のIDを名乗れる。**line.py の `looks_like_our_token` →
LINEへ verify、の順はそのまま使える。

**② 同じLINEを2人に付けない。**
ご夫婦で1台という場合がある。`admin_member.py` に重複を弾く作りは
入っているが、**弾いたときにお客様へ何と出すか**が未決。

**③ 飛ばせるようにする。**
LINEをお使いでない方、つなぎたくない方がいる。
**ログインを止める作りにしない。**

**④ iPhoneでホーム画面から開いた場合。**
LINEの画面へ行って戻る間に、アプリの状態を保てるか。
**実機で確かめるまで言い切れない。**ここだけ机上で判断しない。

## 何のために集めるか（2026-09-08 に伺えた）

```
お客さんの一元管理をLINEIDで行いたい
予約システムの中で、予約者の情報を一つの会員情報から拾ってきたい
```

**この案内は、その入口になる。**台帳の `line_user_id` が空のままでは
予約システムが会員を引けないので、**ここを先に済ませないと先へ進めない。**

形は [お客様台帳を1つにする](お客様台帳を1つにする.md) に書いた。
