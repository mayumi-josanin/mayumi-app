# 窓口はGASのまま

**2026-09-05。[切り替えの段取り](切り替えの段取り.md) の前提が誤っていたことが
分かったため、進め方を書き直す。**

---

## 何が間違っていたか

段取りは「`app.js` の `GAS_URL` を1行、サーバーに向ければ切り替わる」と
書いていた。**お客様アプリのことしか考えていなかった。**

```
お客様アプリ → サーバー（PostgreSQL）    会員・お知らせ・商品を読み書き
管理アプリ   → GAS → スプレッドシート    同じものを読み書き
```

**同じ表に「正」が2つできる。**

| 起きること | |
|---|---|
| 院長がお知らせを投稿 | 管理アプリ→シート。**お客様のアプリには出ない** |
| 受付がスタンプを押す | 管理アプリ→シート。**お客様のアプリでは増えない** |
| お客様がプロフィールを変える | アプリ→サーバー。**管理画面には出ない** |
| お客様がスタンプを取る | アプリ→サーバー。**管理画面には出ない** |

### すでに、ずれている

2026-09-05 に本番とサーバーを並べて数えた。

```
GAS(本番)   お知らせ 91件   いちばん新しい 2026-09-02
サーバー     お知らせ 88件   いちばん新しい 2026-08-18
```

**8/18 以降の3件がサーバーに無い。**院長は今も投稿されている。
この日に切り替えていたら、3件が消え、以後の投稿は一切出なかった。

### 両方を切り替えることはできない

管理アプリが使う窓口は **60種類。サーバーにあるのは4つだけ。**

```
addCategory  broadcastPush  deleteUser  getAdminUsers  getAnalytics
mergeUsers   updateAdminUser  updateProduct  …  （56個が無い）
```

9/19 までに56個を作るのは無理。作れたとしても、**一度に両方を切り替えるのは
戻せない賭けになる。**

---

## 正しい形は、すでに決まっていた

[移行設計](移行設計.md) が **2026-08-15 に方針変更**していた。

> **D. 移す単位は → アプリ単位ではなく「表」単位**
>
> 当初は「管理側だけ移す」としていたが、これは**同じ情報が2か所にできる**
> 危険な形だった。**正しい切り方は「表」単位。**

そして窓口については、こう書いてある。

```
お客様のアプリ ─┐
                ├→ GAS ─┬→ Funnel → PostgreSQL（引っ越し済みの表）
管理アプリ ─────┘        └→ スプレッドシート（まだの表）
```

**段取り（08-23）は、この設計から離れてしまっていた。**設計に戻す。

## これからの進め方

### 変えないもの

- **`app.js` は触らない。**通信先はGASのまま
- **管理アプリも触らない。**通信先はGASのまま
- お客様の札・会員ID・画面のURL も当然そのまま

**アプリを一切変えないので、キャッシュも版数も関係ない。**
お客様の端末に古い版が残る問題が、はじめから起きない。

### 変えるもの

**GASの中身だけ。**表ごとに、シートを読み書きしている所を
サーバーへの転送に置き換える。

```
いま    handleUpdateUser → シートに書く
これから handleUpdateUser → サーバーへ転送（UrlFetchApp + X-Api-Key）
```

段階Bで作った窓口（読み12・書き9）が、そのまま転送先になる。**無駄にならない。**

### 表を1つずつ

| 表 | GASで触っている関数 | 備考 |
|---|---|---|
| お知らせ | 少ない | **最初はここ。**仕組みを確かめるのに向く |
| 商品・メニュー・カレンダー | 中 | |
| **会員** | **59個**（うち外向きの窓口 25個） | いちばん大きい。最後に |

**1つ移すたびに、両方の画面で確かめてから次へ進む。**

### 戻し方

**GASのデプロイを1つ前の版に戻すだけ。**アプリは何も変わっていないので、
お客様の端末に手を入れる必要がない。**戻す速さは、いままでで一番速い。**

---

## 9/19 に何をするか

シルバーウィークの休みは、**そのまま使える。**やることが変わるだけ。

```
9/19(土)  お知らせの表を移す（いちばん小さい。仕組みを確かめる）
9/20(日)  問題が無ければ、商品・メニュー・カレンダー
9/21(月)  ここまでで様子を見る。戻す判断の期限
9/22〜23  会員の表に着手（大きいので、休み中に終わらなくてよい）
```

**全部を1日で終わらせない。**休みが4日あるのは、一度にやるためではなく、
1つずつ確かめながら進めるため。

## この誤りから学んだこと

**「1行変えるだけ」と書いてある手順は疑う。**

段取りには「切り替えるのは1行だけ。だからこそ、戻すのも1行」と書いてあり、
その簡潔さが正しさの証のように見えていた。**実際には、もう一方のアプリを
数に入れ忘れていただけだった。**

見つかったのは、注文の窓口を作ろうとして「注文は管理アプリで見るものだ」と
気づいたため。**作る前に、誰がその表を見るのかを数える。**
